# 2026-10-16 — Erros no chat do Copilot: HTTP 500 (extensão) + HTTP 429 (router LiteLLM)

> **Escopo:** diagnóstico de operação do caminho de **chat via stack** (proxy LiteLLM
> :4000). Arquivo local-only (`reports/` é gitignored — ver `reports/README.md`
> §"Escopo NovAI"). Capturado durante sessão de planejamento da trilha de testes NovAI.
>
> **Natureza:** são **dois erros independentes** — um da extensão Copilot (client-side) e
> um do **nosso** router LiteLLM. Nenhum dos dois é bug do gateway NovAI.

## 0. Resumo

| # | Erro | Origem | Gravidade | Classificação |
| --- | --- | --- | --- | --- |
| 1 | `500 Server error` | Extensão Copilot (client-side, `extension.js`) | Cosmético | Não é nosso, nem do gateway |
| 2 | `429 all_deployments_in_cooldown` (`deepseek-flash-fast`) | **Router LiteLLM (nosso)** | Real (robustez) | Config ausente de `router_settings` |

**Achado principal:** o 429 citou `model=deepseek-flash-fast`, que é uma rota do **nosso**
`litellm/config.yaml` (linha 167). Ou seja, o chat estava roteado pelo **proxy local :4000**
— o erro veio da camada de router do LiteLLM, **não** do gateway NovAI.

## 1. Erro 1 — HTTP 500 da extensão Copilot (client-side)

### Sintoma

```
Sorry, your request failed. Please try again.

Reason: Server error: 500: Error: Server error: 500
  at RH._provideLanguageModelResponse (.../extensions/copilot/dist/extension.js:1614:15814)
  at process.processTicksAndRejections (node:internal/process/task_queues:104:5)
  at async RH.provideLanguageModelResponse (.../extension.js:1614:17008)
```

### Evidência

- **Client Request Id:** `bebc1dc0-8eb0-45e9-9a73-4808bbf15962` (ocorreu mais de uma vez).
- Caminho real do binário: `/home/demo/.vscode-server/bin/6d62b1d5dace93a33b3a6d3eca1317bd5e15bcb1/extensions/copilot/dist/extension.js`.

### Análise

- Erro **interno da extensão Copilot** — ocorre no cliente, **antes/depois** do proxy.
  Não é HTTP 500 do LiteLLM nem do gateway.
- Causa provável: **contexto muito grande** na sessão de chat (o agente havia lido um
  dump de memória de repositório com milhares de linhas) — mesma classe da "pressão de
  janela" documentada no repo (H1/H6). Também possível: bug transitório da extensão.
- **Não bloqueia** o trabalho; recorrente apenas em sessões longas.

### Ação

- **Sem ação de código.** Mitigação operacional: **abrir um chat novo** quando a sessão
  ficar longa (reduz a cauda não-cacheada e o risco de reincidência).
- Se reincidir de forma persistente, escalar para o suporte do Copilot com o
  `Client Request Id` acima.

## 2. Erro 2 — HTTP 429 `all_deployments_in_cooldown` (router LiteLLM)

### Sintoma

```
Rate limit exceeded
{"message":"No deployments available for selected model, Try again in 5 seconds. All
 deployments for selected model are in cooldown. Passed model=deepseek-flash-fast.
 pre-call-checks=False,
 cooldown_list=['da057351fa05e1a715c2ba2b7285e40a70432a2c724ef772d6ed6fdf72ae57fb']",
 "type":"all_deployments_in_cooldown","param":null,"code":"429"}
  at RH._provideLanguageModelResponse (.../copilot/dist/extension.js:1614:15755)
```

### Evidência

- **Client Request Id:** `5db9fc30-d37c-4e34-ab2b-20c5514c8733`.
- Payload é o **router do LiteLLM** (`type=all_deployments_in_cooldown`), não o gateway.
- `model=deepseek-flash-fast` = grupo do `litellm/config.yaml` (linha 167) com **1 único
  deployment** (`deepseek/deepseek-flash`).

### Análise (causa raiz)

1. O grupo `deepseek-flash-fast` tem **um só deployment** — sem redundância.
2. Quando esse deployment falha, o router o coloca em **cooldown** e **não há alternativa**
   para rotear → responde **429 imediato** (`all deployments in cooldown`), mesmo com
   `num_retries: 2` (retries só acontecem se houver deployment saudável).
3. **`litellm/config.yaml` NÃO tem bloco `router_settings`** (confirmado por grep — só
   existe `num_retries: 2` em `litellm_settings`). Logo `allowed_fails`, `cooldown_time`,
   `disable_cooldowns` e `fallbacks` do router ficam nos **defaults do LiteLLM**.
4. "Try again in 5 seconds" = cooldown curto ⇒ o 429 é **recuperável** (retry manual/novo
   turno passa).

### Escopo

- **Nosso (camada proxy)**, não é bug do gateway NovAI. Atinge grupos de **1 deployment**
  em cooldown — hoje, todas as rotas multi-provedor do config (novai-*, deepseek-*, qwen3.8-*)
  têm 1 deployment por grupo.

### Ação proposta

- **Item de robustez (novo):** definir `router_settings` no `litellm/config.yaml`:
  - `allowed_fails` (ex.: 3) — tolerar falhas antes de abrir cooldown;
  - `cooldown_time` (curto, ex.: 5–30 s) — alinhado ao "Try again in 5 seconds" observado;
  - `disable_cooldowns` (avaliar) — se o custo de servir pela rota em cooldown for menor
    que o impacto de um 429;
  - opcional: **fallback chain** por grupo (ex.: `deepseek-flash-fast` → candidato alternativo).
- Ler os **blocos de comentários do `config.yaml`** antes de editar (são o registro das
  decisões de routing — regra §G.4 do backlog).
- Aceite: `pytest` verde + invariante 7 do `10-STATE.md` §4 preservado (aliases acoplados
  ao código; chat fora do cache de resposta).

## 3. Relação com a trilha de testes NovAI (S102)

Este incidente **valida a necessidade do workstream de logging** da trilha NovAI
("erros no chat que não foram capturados"): o harness `eval/novai_test.py` deve gravar,
por chamada, uma linha jsonl com `status=success|failure` (sucesso **e** falha) em
`reports/logs/<data>-novai-<family>.jsonl`, com request sanitizado + headers + body raw +
latência + erro. O erro 2 (429 de cooldown) seria capturado nativamente por essa camada.

## 4. Reprodução

- Erro 1: sessão de chat longa no Copilot (VS Code/code-server). Sem repro determinística.
- Erro 2: forçar falha num grupo de 1 deployment e chamá-lo em seguida (o router põe em
  cooldown e o próximo request responde 429). Observável em `LiteLLM_SpendLogs` como
  `status=failure` + `type=all_deployments_in_cooldown`.
